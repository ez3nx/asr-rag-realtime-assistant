
# ML System Design Doc - [RU]

## Дизайн ML системы – ASR-RAG-Realtime-Assistant, MVP, Итерация 1

*Шаблон ML System Design Doc от телеграм-канала [Reliable ML](https://t.me/reliable_ml)*

---

### 1. Цели и предпосылки

#### 1.1. Зачем идем в разработку продукта?

- **Бизнес-цель.**
  Сократить среднее время обработки обращения (Average Handle Time), снизить нагрузку на операторов и повысить качество ответов за счет оперативного доступа к актуальной базе знаний и лучшим практикам ответа.

- **Почему станет лучше, чем сейчас, от использования ML.**
  Сейчас оператору необходимо:
  - самостоятельно формулировать запросы к базе знаний / внутренним системам;
  - вручную искать релевантные статьи и скрипты;
  - запоминать большое количество сценариев и исключений.
  Использование online-ASR + RAG позволит:
  - автоматически извлекать ключевой контекст из диалога;
  - формировать запросы к базе знаний без участия оператора;
  - возвращать оператору готовые подсказки/шаблоны ответов в течение нескольких секунд.

- **Что будем считать успехом итерации с точки зрения бизнеса.**
  Для пилотной итерации (MVP) успехом считаем:
  - сокращение среднего времени поиска ответа оператором (прокси-метрика: доля кейсов, где оператор воспользовался подсказкой вместо самостоятельного поиска);
  - положительную обратную связь от не менее чем X % операторов пилотной группы (оценка полезности подсказок по опросу);
  - отсутствие роста количества эскалаций/ошибочных ответов на пилотной группе по сравнению с контрольной;
  - достижение технологической задержки подсказки не более N секунд с момента произнесения релевантной реплики абонента (конкретные значения X, N уточняются с бизнесом).

#### 1.2. Бизнес-требования и ограничения

- **Краткое описание бизнес-требований.**
  - Подсказки должны отображаться оператору в интерфейсе рабочего места вблизи real-time.
  - Система не должна автоматически отправлять сообщения абоненту; окончательное решение и формулировка ответа остаются за оператором.
  - Подсказки должны быть основаны на утверждённой базе знаний (регламент, скрипты, FAQ), а не на «галлюцинациях» модели.
  - Решение должно работать как минимум для входящих голосовых обращений на русском языке в рамках заданного пилотного сценария (либо сегмента процессов).

- **Бизнес-ограничения.**
  - Ограниченный бюджет и сроки на первую итерацию (MVP) → приоритет простоты решения и скорости поставки над максимальной точностью.
  - Жёсткие требования к качеству и соответствию регламентам (особенно в отраслевых доменах: финансы, телеком, госуслуги).
  - Наличие существующей инфраструктуры контакт-центра и рабочего места оператора, в которую нельзя вносить радикальные изменения на этапе пилота.
  - Требования по защите персональных данных (ФИО, номера телефонов, договоры и т.п.) – возможные ограничения на хранение и использование разговоров для обучения.

- **Ожидания от конкретной итерации (MVP).**
  - Реализовать вертикально завершённый прототип: от получения аудио до отображения подсказки оператору.
  - Ограничиться одним/несколькими приоритетными сценариями обращения (например, типовые вопросы по тарифам, статусу заявки, базовым операциям).
  - Использовать одну доменную базу знаний, подготовленную вручную (конфигурация источников данных минимальна, без сложной интеграции).
  - Пилот проводится на ограниченной группе операторов, в ограниченное время, с фиксацией качественных и количественных метрик.

- **Описание бизнес-процесса пилота.**
  - Абонент звонит в контакт-центр и попадает к оператору стандартным способом.
  - Аудиопоток разговора параллельно поступает в ASR-модуль (через интеграцию с телефонией или через дубликат аудиопотока).
  - Система в режиме реального времени распознает речь, определяет намерение (intent) и при необходимости запускает RAG-пайплайн.
  - В интерфейсе оператора (отдельная панель/виджет) отображаются:
    - 1–3 релевантные подсказки с кратким текстом и/или ссылкой на статью базы знаний;
    - ключевые извлечённые факты (например, тип запроса, продукт, статус).
  - Оператор использует подсказку или игнорирует её, общаясь с клиентом в обычном режиме.
  - По результатам пилота собираются метрики и обратная связь операторов.

- **Критерии успешного пилота и возможные пути развития.**
  - Достигнуты целевые или близкие к целевым значения по прокси-метрикам (доля использованных подсказок, субъективная полезность, отсутствие роста жалоб).
  - Есть подтверждённые гипотезы о том, какие типы запросов лучше всего покрываются системой.
  - Выявлены узкие места (latency, качество ASR, релевантность RAG), сформирован бэклог улучшений.
  - При успехе пилота – масштабирование на большее число операторов и/или сценариев, интеграция с дополнительными источниками знаний.

#### 1.3. Что входит в скоуп проекта/итерации, что не входит

- **Входит в скоуп данной итерации (MVP).**
  - Online/near real-time распознавание речи (ASR, STT) для одного языка (русский) и заданного домена разговоров.
  - Базовый модуль intent classification для определения, когда запускать RAG-пайплайн и какие области знаний релевантны.
  - RAG-пайплайн:
    - подготовка и индексация ограниченной базы знаний (регламенты, скрипты, FAQ);
    - поиск релевантных фрагментов (retrieval);
    - генерация краткой текстовой подсказки оператору на основе найденного контента.
  - Простой интерфейс отображения подсказок оператору (прототип; допускается отдельное окно/веб-интерфейс).
  - Базовый логгинг: сохранение ключевых событий (распознанный текст, сработавший intent, выбранные документы, показанные подсказки).

- **Не входит в скоуп данной итерации.**
  - Автоматическая отправка ответов абоненту без участия оператора.
  - Автоматическая маршрутизация звонков, IVR, голосовые боты.
  - Глубокая персонализация подсказок под конкретного абонента на основе истории взаимодействий.
  - Полноценная высоконагруженная продакшн-инфраструктура (multi-region, auto-scaling, 24/7 SLO и т.п.).
  - Многоязычная поддержка и поддержка разных стран/юрисдикций.

- **Ожидаемый результат с точки зрения качества кода и воспроизводимости.**
  - Репозиторий с воспроизводимым прототипом:
    - зафиксированные зависимости;
    - базовые скрипты/ноутбуки для запуска ASR и RAG на тестовых данных;
    - описание пайплайна и артефактов (дизайн-док, README).
  - Наличие минимальных практик качества кода: линтеры, форматирование, pre-commit.
  - Возможность развернуть и воспроизвести MVP в другом окружении при наличии доступа к исходным данным.

- **Планируемый технический долг.**
  - Упрощённая архитектура пайплайна (монолитный сервис/скрипт вместо модульной микросервисной архитектуры).
  - Отсутствие полноценного мониторинга качества моделей и деградации (возможен только ручной анализ логов на этапе MVP).
  - Ограниченная проработка тематики данных (часть редких сценариев и edge-cases не покрывается).
  - Отложенная оптимизация стоимости инфраструктуры и масштабируемости до этапа после успешного пилота.

#### 1.4. Предпосылки решения

- **Наличие данных.**
  - В организации есть записи звонков/разговоров и/или возможность организовать запись для пилота.
  - Доступна и может быть подготовлена структурированная база знаний (регламенты, скрипты, внутренние статьи).

- **Технические предпосылки.**
  - Существующая телефония/платформа контакт-центра позволяет получить аудиопоток в реальном времени или с минимальной задержкой.
  - Допускается развёртывание дополнительного сервиса (ASR+RAG) в инфраструктуре компании или в допустимом облаке.
  - Ожидаемая нагрузка в пилоте ограничена (ограниченное количество операторов и одновременных звонков).

- **Модели и подходы.**
  - Для ASR планируется использовать существующую предобученную модель с поддержкой русского языка (облачный сервис или open-source модель).
  - Для RAG планируется использовать:
    - векторное представление документов из базы знаний;
    - поиск ближайших соседей;
    - генерацию ответа/подсказки LLM-моделью, ограниченной найденным контекстом.

- **Бизнес-предпосылки.**
  - Есть заинтересованный заказчик (business owner) со стороны контакт-центра.
  - Есть ресурсы (несколько операторов и временной слот) для проведения пилота и сбора обратной связи.

### 2. Методология `Data Scientist`

#### 2.1. Постановка задачи

- **Тип задачи.**
  - Потоковое распознавание речи (ASR, STT).
  - Классификация намерений (intent classification) и/или триггерных событий в диалоге.
  - Поисково-рекомендательная задача: retrieval-augmented generation (RAG) подсказок оператору на основе базы знаний.

- **Формулировка задачи в терминах ML.**
  - Вход:
    - аудиопоток разговора оператор–абонент;
    - метаданные звонка (при наличии: тип обращения, линия, продукт).
  - Выход:
    - транскрипт диалога в (quasi-)real-time;
    - список ключевых намерений/тем диалога;
    - 1–3 текстовые подсказки оператору, основанные на релевантных статьях базы знаний.

- **Цели с точки зрения качества ML-компонентов (черновые).**
  - ASR: приемлемый уровень WER/CER для домена пилота (конкретные значения определяются по результатам тестирования).
  - RAG: достаточная релевантность подсказок для основных сценариев (оценка по экспертизе и обратной связи операторов).
  - Latency: суммарная задержка от фразы абонента до появления подсказки не более заранее согласованного порога.

#### 2.2. Блок-схема решения

Блок-схема описывает высокоуровневый пайплайн для MVP (baseline может рассматриваться как упрощённый вариант без части компонентов).

1. **Получение аудио.**
   - Подключение к аудиопотоку звонка (одна или две дорожки: оператор, абонент).
   - Потоковая передача аудио в ASR-сервис.

2. **Онлайн-ASR.**
   - Разбиение аудио на фрагменты (чанки) и распознавание речи в реальном времени.
   - Формирование временных меток и атрибуция реплик (кто говорит).

3. **Intent classification / выявление триггеров.**
   - Анализ текущего и предыдущих фрагментов транскрипта.
   - Определение намерения/темы запроса или триггера для запуска RAG (например, «вопрос по тарифу», «статус заявки», «техническая проблема»).

4. **Формирование запроса к базе знаний (RAG).**
   - Построение текстового запроса на основе текущего контекста диалога и распознанного интента.
   - Поиск релевантных документов/фрагментов в векторном хранилище или другой системе поиска.

5. **Генерация подсказки.**
   - Формирование кандидатов подсказок на основе найденного контента:
     - краткое резюме релевантной статьи;
     - список шагов, которые должен предпринять оператор;
     - возможные уточняющие вопросы.
   - (Опционально) использование LLM для генерации финальной формулировки с ограничением контекстом найденных документов.

6. **Отображение подсказок оператору.**
   - Отправка подсказки в фронтенд/виджет рабочего места оператора.
   - Обновление подсказок по мере изменения контекста диалога.

7. **Логгирование и телеметрия.**
   - Сохранение транскриптов (при соблюдении требований по безопасности данных).
   - Логгирование срабатывания интентов, выбранных документов и показанных подсказок.
   - Сбор сигналов для последующего анализа и улучшения моделей.

> В дальнейшем к данной блок-схеме могут быть добавлены отдельные схемы для бейзлайна (например, ручной запуск поиска по ключевым словам без RAG) и для продакшн-архитектуры.

### 4. Внедрение (для production систем, если требуется)

В данной итерации фокус на MVP и пилоте; детали продакшн-внедрения, инфраструктуры и масштабируемости будут проработаны после успешного пилота.
